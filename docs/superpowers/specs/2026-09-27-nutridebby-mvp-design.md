## 1. Visão

SaaS de gestão de consultório nutricional com portal do paciente em PWA. Referência de mercado: Dietbox.
O produto nasce **multi-tenant**, mas o **onboarding é manual**: o admin da plataforma cria cada conta de nutricionista. A primeira cliente é a Debby. Cobrança da assinatura e cadastro pela própria nutricionista ficam para a Fase 2 (Abordagem A, aprovada em 2026-09-27).

### 1.1 Critérios de sucesso do MVP

| ID | Critério | Como medir |
|---|---|---|
| CS-01 | A Debby atende **100% dos pacientes** pelo sistema por **30 dias consecutivos**, sem voltar à ferramenta anterior | Confirmação da Debby + consultas registradas × agenda. **v1.11 (Plano 08, D15):** consultas `realizada` com atendimento registrado ÷ consultas `realizada` desde `tenants.go_live_em` ("Início do uso", informado pelo admin), mais "Dias desde o início: N de 30"; o "sem voltar à ferramenta anterior" é a confirmação da Debby (D15); o checklist do go-live (`docs/operacao/go-live.md`) registra o dia em que o CS-01 começa a contar |
| CS-02 | **≥ 60% dos pacientes ativos** abrem o PWA pelo menos 1× por semana | Métrica de sessões por paciente (tabela de eventos de acesso). **v1.11 (Plano 08, D15):** conta **dias com acesso** (`access_events`), não sessões: pacientes `ativo`, **com conta no portal** e não anonimizados que abriram o app nos últimos 7 dias (no fuso do tenant) ÷ esses mesmos pacientes (`META_CS02 = 0.6`), com as barras dos 7 dias |
| CS-03 | Taxa de faltas **menor** que a do mês anterior ao sistema | `appointments.status = 'faltou'` / consultas do mês. **v1.11 (Plano 08, D15):** a taxa do mês (já no Início desde o Plano 05) contra a **taxa-base** informada pelo admin (`tenants.taxa_faltas_base`, "Taxa de faltas antes do sistema (%)"; P-15) |

**v1.11 (Plano 08, P08-07):** os números saem de `metricasDeSucesso` (`src/modules/plataforma/metricas-sucesso.ts`, só contagens e sem `auditRead`, numa transação) e aparecem no Início do painel — cartões "Pacientes no app esta semana" ("{abriram} de {total} pacientes abriram o app nos últimos 7 dias") e "Critérios de sucesso" ("Atendimentos registrados: {x} de {y} consultas realizadas ({pct})", "Dias desde o início: {n} de 30", "Taxa de faltas antes do sistema: {pct}%"). O admin vê só contagens por tenant, pela função `SECURITY DEFINER` `admin_metricas_sucesso()` (migration 0087; colunas "App na semana" e "Faltas no mês"), e grava a base e o início do uso no próprio painel ("Taxa de faltas antes do sistema (%)", "Início do uso", "Métricas salvas.").

## 3. Perfis de acesso

| Perfil | Pode | Não pode |
|---|---|---|
| **Admin da plataforma** | Criar, suspender e reativar tenants; ver métricas agregadas de uso (nº de pacientes, consultas, mensagens enviadas, cota de WhatsApp — **Plano 02:** `admin_tenant_metrics()` já devolve essas colunas, com `NULL` até as tabelas existirem, nos Planos 03 e 05; arquivos e armazenamento já são contados de verdade; **Plano 05:** `consultas_mes` e `mensagens_whatsapp_mes` passam a ser contagens reais, no mês civil do fuso do tenant); ajustar a cota de WhatsApp do tenant; **v1.11 (Plano 08, D15):** ver as contagens do CS-02 e do CS-03 por tenant (`admin_metricas_sucesso()`, migration 0087) e gravar a taxa de faltas antes do sistema e o início do uso (§1.1) | Ler prontuário, plano, diário, exames ou qualquer dado de saúde. Exceção: suporte a um caso específico, **com autorização registrada da nutricionista** e com o acesso auditado (Fase 2; no MVP não há essa tela) |
| **Nutricionista** (dona do tenant) | Tudo dentro do próprio tenant | Ver dados de outro tenant |
| **Paciente** | Ver o próprio plano publicado, a evolução, as orientações e a agenda; preencher o diário; agendar/remarcar dentro das regras; ver os conteúdos destinados a ele; exportar os próprios dados | Ver `notas_privadas`, planos em rascunho, dados de outros pacientes |

**2FA:** obrigatório para o admin; opcional (recomendado) para a nutricionista.

**Modelo de identidade:** o login (`users`) é global por e-mail e tem **um único papel**. No MVP, uma nutricionista que também seja paciente de outra precisa usar outro e-mail. O prontuário (`patients` e dependentes) pertence ao tenant. Um mesmo usuário pode ser paciente de mais de um tenant; cada nutricionista vê só o próprio histórico. No PWA, se houver mais de um vínculo, o paciente escolhe a nutricionista ao entrar. **v1.9 (Plano 06):** a escolha fica no cookie `nd_vinculo` (só o `tenantId`, `httpOnly`, `SameSite=Lax`, 30 dias, renovado a cada abertura do portal) e é reconferida a cada requisição contra os vínculos ativos da conta; com um vínculo só, entra direto; "Trocar de nutricionista" em "Perfil". Vínculo arquivado, bloqueado ou anonimizado some da lista (RN-08); o consultório suspenso barra só aquele vínculo (RN-15).

## 4. Arquitetura

```
Paciente (PWA)  /  Nutricionista (web)  /  Admin
            │  HTTPS — Traefik (Easypanel) + Let's Encrypt
            ▼
┌─────────────────────────────────────────────────────────────┐
│ nutri_app     Next.js 16 (App Router): UI + Route Handlers  │
│               + Server Actions; monólito modular M1–M6      │
├─────────────────────────────────────────────────────────────┤
│ nutri_worker  mesma imagem, comando `worker`: pg-boss       │
│               (lembretes, e-mails, WhatsApp, push, PDFs,    │
│               imagens; só confere o backup e alerta)        │
├─────────────────────────────────────────────────────────────┤
│ nutri_db      PostgreSQL 16 — RLS por tenant_id; também     │
│               guarda a fila pg-boss (sem Redis)             │
├─────────────────────────────────────────────────────────────┤
│ volume /data  PDFs de exames/planos, fotos do diário, capas,│
│               logos — montado no app e no worker (mesmo nó) │
│               servidos só por URL assinada, TTL 5 min       │
└─────────────────────────────────────────────────────────────┘
            │ backup diário criptografado (rclone, rodando no host)
            ▼
     Cloudflare R2 (offsite)

Externos: Resend (e-mail) · Web Push (VAPID) · Sentry ·
          Cloudflare Turnstile (anti-robô na página pública) · GHCR (imagens)
Na VPS (v1.8): nutri_evolution — Evolution API v2.3.7 (WhatsApp), sem domínio,
          só na rede interna; banco `evolution` próprio dentro do nutri_db
```

### 4.1 Organização do código

Monólito modular: `src/modules/{plataforma,pacientes,planos,agenda,portal,conteudo}` (**Plano 04:** `planos` virou dois módulos, `alimentos` e `plano-alimentar`; **Plano 05:** a agenda são dois módulos, `agenda` e `notificacoes` — o motor de envio também serve o convite do paciente, US-010; **Plano 06:** `portal` — vínculos da conta, acesso diário, plano, diário, evolução, lista de compras, pedidos do titular e inscrição de push —, com a sessão de paciente em `src/lib/paciente-session.ts`). Cada módulo expõe funções de domínio (**Plano 02:** em vários arquivos por módulo, como `contas.ts` e `convites.ts`, em vez de um único `service.ts`). As rotas e a UI chamam só o módulo, nunca o banco direto. O acesso ao banco passa por um helper `withTenant(ctx, fn)`, que abre a transação e executa `SET LOCAL` de `app.tenant_id`, `app.role` e, para sessões de paciente, `app.patient_id`, antes de qualquer consulta. **v1.9 (Plano 06):** a sessão de paciente entra por `requirePaciente(path)` (páginas e Server Actions do portal) e `requireApiPaciente(req)` (rotas `/api/p/…`), que devolvem o contexto pronto (`role: 'paciente'`, `tenantId` e `patientId` do vínculo escolhido, `actorUserId`, `ip`); o tenant e o paciente vêm sempre dos vínculos da conta; o `?v=` da URL é só uma preferência, reconferida contra os vínculos ativos (consultório não suspenso). **v1.10 (Plano 07):** `conteudo` — link e player (`video.ts`), oEmbed (`oembed.ts`), capa (`capa.ts`), markdown (`markdown.tsx`), núcleo e arquivos do conteúdo (`conteudos.ts`, `arquivos.ts`), audiência (`audiencia.ts`), receitas (`receitas.ts`, `receita-calculo.ts`), aviso de conteúdo novo (`aviso.ts`), métricas (`metricas.ts`) e LGPD (`titular.ts`) —; o portal lê os conteúdos por `src/modules/portal/conteudos.ts`. A conferência de mesma origem dos `POST` de Route Handler fica num lugar só, `mesmaOrigem(req)` (`src/lib/mesma-origem.ts`, S-9: `Origin` presente e diferente — inclusive vazio ou `null` — é recusado; o `/sair` mantém a regra própria, mais estrita). **v1.11 (Plano 08):** observabilidade em `src/lib/sentry.ts` e `src/lib/sentry-filtro.ts` (RNF-11), `request_id` em `src/lib/request-id.ts`, CSP em `src/lib/csp.ts` (RNF-06), tokens de cor em `src/lib/tema/` (§4.3), o manual guiado em `src/modules/ajuda/conteudo.ts`, as preferências da conta em `src/modules/plataforma/preferencias.ts` e as métricas de sucesso em `src/modules/plataforma/metricas-sucesso.ts`; o cabeçalho de todas as telas do painel sai de `src/app/painel/layout.tsx` (o layout **não** é barreira de segurança: toda página continua chamando `requireNutri`). **Ator obrigatório (N7):** `withTenant` recusa `nutri` sem `actorUserId` e `paciente` sem `actorUserId`, salvo com `semConta: true` — a marca explícita dos três fluxos de paciente sem login, lista fechada `SEM_CONTA_PERMITIDOS` (`src/modules/agenda/acoes-link.ts`, `src/modules/notificacoes/whatsapp/webhook.ts`, `src/modules/pacientes/convite-paciente.ts`; guarda `sem-conta-guarda.test.ts`), que mantêm a RLS por paciente e o `audit_log` sem ator.

Regras de acesso que complementam a RLS:
- **Paciente só vê o que é dele:** nas tabelas 🔒 com `patient_id`, uma segunda política RLS exige `patient_id = app.patient_id` quando `app.role = 'paciente'`. Assim, um erro no service não expõe outro paciente do mesmo tenant.
- **Escrita do paciente negada por padrão (v1.9, Plano 06, D1 — resolve a P-16 a):** `app_enable_tenant_rls` cria em toda tabela com `tenant_id` (as antigas pela migration 0070 e as futuras pela própria função) as políticas `RESTRICTIVE` `paciente_sem_insert`, `paciente_sem_update` e `paciente_sem_delete`. Só o que o portal e os fluxos do paciente gravam é liberado, por comando, com `app_allow_paciente_escrita`, e a lista `PACIENTE_ESCREVE` (`src/db/rls-guard.ts`, com o motivo de cada liberação) tem de bater com o banco (guarda `findPacienteEscritaViolations` no CI): `patients` (`update`), `appointments` (`insert`, `update`), `notifications` (`insert`, `update`), `audit_log` (`insert`), `stored_files` (`insert`), `access_events` (`insert`), `push_subscriptions` (`insert`, `delete`), `diary_entries` (`insert`), `privacy_requests` (`insert`), `data_exports` (`insert`, `update`). `foods`, `food_measures`, `anamnesis_templates` e todo o prontuário (antropometria, exames, planos, atendimentos…) ficam fechados para a sessão de paciente. Sem a política de `UPDATE`, um `SELECT … FOR UPDATE/SHARE` do paciente não enxerga a linha. **Reforço da migration 0080 (decisão do dono, 03/10/2026; defesa em profundidade):** o banco também confere **o que** a sessão de paciente grava — `paciente_diario_insert` em `diary_entries` (sem foto convertida, comentário nem "visto"; `foto_status` só `sem_foto`/`processando`; a foto original, se houver, tem de ser um `stored_files` `diario_foto_original` do próprio paciente), `paciente_exportacao_titular` em `data_exports` (o paciente só vê, cria e altera pedidos de `escopo = 'titular'`) e `paciente_arquivo_insert` em `stored_files` (o paciente só grava `tipo = 'diario_foto_original'`). Ficam fora dessa negação as tabelas fora da RLS: as sem `tenant_id` (`tenants`, `session`, `account`, `verification`, `two_factor`, `backup_runs`, `public_rate_limits`) e as com `tenant_id` listadas em `RLS_EXCEPTIONS` (`user`, `consents`, `invites`; `consents` é gravada pelo aceite do termo no portal, `src/modules/portal/termo.ts`) (limite conhecido, P06-12). **v1.10 (Plano 07):** `PACIENTE_ESCREVE` ganha `content_views` (`insert`) e `content_favorites` (`insert`, `delete`), conferidas também pela audiência (item abaixo); a guarda passa a conferir também a **expressão** de cada `paciente_sem_*` (`app_current_role() IS DISTINCT FROM 'paciente'`), não só o nome, o comando e o `RESTRICTIVE` (B-5). **v1.11 (Plano 08, migration 0085 — B-4, B-6, N38):** o banco confere também as **colunas** que a sessão de paciente altera, com gatilhos `BEFORE UPDATE` `paciente_colunas` que recusam com 42501: em `patients`, só `user_id` (de nulo para a própria conta — o aceite do convite), as colunas do WhatsApp (opt-in novo com origem `paciente`, ou opt-out a partir de agora sem mexer no opt-in: a prova do consentimento dado pela nutricionista não é reescrita nem reativada) e `updated_at`; em `data_exports`, só `status` de `pendente` para `falhou` (e `updated_at`). `audit_log` ganha a `RESTRICTIVE` `paciente_sem_leitura` (`FOR SELECT`): a sessão de paciente não lê nem as próprias linhas (o `auditRead` e o gatilho de auditoria só fazem `INSERT`). Em `stored_files`, a `paciente_arquivos` passa a mostrar ao paciente só a **capa de conteúdo** que a RLS da audiência já deixa ele ver (`EXISTS` em `contents`, inclusive com a liberação das receitas do plano), além dos próprios arquivos e do logo. **v1.12 (Plano 10A):** mais duas escritas do paciente — `signed_document_receipts` (`insert`: abrir e confirmar o recebimento do próprio documento assinado, só INSERT, `REVOKE UPDATE, DELETE`) e `document_access_codes` (`insert`, `update`: o paciente **sem login** pede e confere o código do link do documento; o gatilho `app_codigo_acesso_regras` só deixa subir `tentativas` de 1 em 1 e abrir a sessão uma vez); a `paciente_arquivos` (refeita na 0090) esconde do paciente o PDF preparado (`documento_base`) e as fotos da digitalizada (`documento_digitalizado`).
- **Documentos assinados (v1.12, Plano 10A — receita):** módulo novo `src/modules/documentos` (spec [`2026-10-03-nutridebby-documentos-assinados-design.md`](2026-10-03-nutridebby-documentos-assinados-design.md) v0.4). Contextos: painel = `nutri`; portal = `paciente`; **link do documento por e-mail = `paciente` com `semConta`** (`src/modules/documentos/link-documento.ts` entra em `SEM_CONTA_PERMITIDOS`, que passa a ter quatro arquivos); PDF preparado, PDF da digitalizada, varreduras e anonimização = `worker`; **verificação pública** (`/v/<código>`) sem contexto de tenant, só pela tabela `document_verifications`, que entra em `RLS_EXCEPTIONS` (sem dado de saúde nem do paciente; só `src/modules/documentos/verificacao.ts` a cita, guarda em `verificacao.test.ts`; `UPDATE` só de `situacao`/`situacao_em`, `DELETE` revogado). `signed_document_notes` (justificativa de uso e motivo de cancelamento) é `staff_only` e entra em `STAFF_ONLY`; `document_access_codes` entra em `AUDIT_EXCEPTIONS` (só HMAC); `signed_documents` tem a política `paciente_so_emitidos` (o paciente vê só assinado, substituído ou cancelado e nunca grava). A imutabilidade do documento emitido é do **banco** (gatilho `app_documento_imutavel`, migrations 0091 e 0093) e a anonimização só pela função `app_anonimizar_documentos` (`SECURITY INVOKER`, só no contexto `worker`, chamada por `anonimizarVencidos` antes dos anexos). Primeiras FKs `NO ACTION` para `stored_files.caminho` (`base_pdf_path`, `pdf_path`). **Interruptor do admin** `tenants.documentos_liberados` (padrão `false`): sem ele, nada de documento aparece para a nutricionista nem para o paciente.
- **IA de leitura de laudos (v1.13, Plano 11):** módulo novo `src/modules/ia` ([spec da IA](2026-10-03-nutridebby-ia-nutricionista-design.md) v0.4). Tabelas 🔒 `ia_tarefas` (por paciente, `staff_only`, auditada com a entidade `ia`; `DELETE` só pelo `worker` com o paciente anonimizado, gatilho `ia_tarefas_sem_apagar`; colunas fixas pelo gatilho `ia_tarefas_imutavel`, 0100) e `ia_uso` (registro técnico sem `patient_id` nem conteúdo, `staff_only`, fora da auditoria, `REVOKE DELETE, TRUNCATE`); `ia_gasto_plataforma` (contador do teto global, **sem `tenant_id`**, fora da RLS como `backup_runs`; só `src/modules/ia/cota.ts` grava). `consents` passa a guardar também o aceite do **aditivo de IA** da nutricionista (`ia-aditivo-<versão>`, com o `tenant_id` do consultório), gravado por `src/modules/plataforma/dpa.ts`. Na `patients`, a ciência e a recusa de IA só mudam pela nutricionista ou pelo worker (gatilho `patients_ia_quem`); na `tenants`, `ia_liberada`, `ia_cota_mensal_usd` e `documentos_liberados` só mudam fora de `withTenant` (gatilho `tenants_interruptores_da_admin`, 0100). Filas `ia` e `expirar-ia` no worker; `@anthropic-ai/sdk` e `pdf-lib` só no worker (guarda de grafo); a chave `ANTHROPIC_API_KEY` só no worker. Travas do tenant nos fluxos da IA em `FOR NO KEY UPDATE`.
- **Contexto `conta` (v1.9, Plano 06, D2):** a conta de paciente não tem tenant (§3). Para achar os vínculos, `withConta(userId, fn)` abre a transação com `app.role = 'conta'` e sem `app.tenant_id`; a única política que libera linhas nesse papel é `paciente_por_conta` em `patients` (`PERMISSIVE`, só `SELECT`, `user_id` = a conta). Toda outra tabela com RLS dá 0 linhas (menos a TACO, pública); as tabelas fora da RLS (`tenants`, por exemplo, lida no join de `vinculosDaConta`) seguem legíveis. Nenhuma escrita passa. Só `src/modules/portal/vinculos.ts` (`vinculosDaConta`) usa o contexto; a função `app_conta_sem_outro_vinculo` (migration 0079, `SECURITY DEFINER`) usa o mesmo papel dentro da anonimização.

- **Push de aparelho compartilhado (v1.9, Plano 06, D26):** um endpoint de push pertence a uma conta. Ativar as notificações, e cada abertura do portal com inscrição no navegador, chamam `app_soltar_endpoint_push` (migration 0075, `SECURITY DEFINER`, só na sessão de paciente), que apaga o endpoint de toda outra conta em qualquer tenant. - **`foods` é a única tabela com `tenant_id` nulo e RLS (Plano 04):** a política `tenant_isolation` continua valendo (escrita só nas próprias linhas) e a política extra `taco_leitura`, só `FOR SELECT USING (tenant_id IS NULL)`, libera a leitura da TACO. A TACO fica imutável para a aplicação: nenhum tenant cria, altera ou apaga linha com `tenant_id` nulo.
- **Tabelas sem `tenant_id`** (`tenants`, `users` — tabelas do Better Auth no Plano 01 — `consents`, `invites`, `backup_runs`, `public_rate_limits`): acesso só pelos services do M1, com verificação explícita de dono; cobertas por testes de autorização. **v1.11 (Plano 08, D17):** as colunas `user.tema` e `user.guia` são lidas e gravadas fora do `withTenant` só por `src/modules/plataforma/preferencias.ts`, sempre com o `userId` da sessão (nunca do formulário); o `tema` chega à sessão pelo `additionalFields` do Better Auth com `input: false` (o `update-user` não grava o campo). As colunas novas de `tenants` (`taxa_faltas_base`, `go_live_em`) seguem a regra de `tenants`: o admin grava, o `tenantId` vem da sessão. **Plano 05:** `push_subscriptions` ganhou `tenant_id` e `patient_id` e entrou na RLS por paciente (o envio roda no `withTenant` do worker e a exclusão LGPD apaga só as do vínculo); `consents` ganhou `patient_id` (com `tenant_id`) para o aceite da página pública e continua fora da RLS, em `RLS_EXCEPTIONS`; `public_rate_limits` (contadores por IP/e-mail com HMAC, e a marca anti-repetição do webhook) só é acessada por `src/modules/agenda/limite-ip.ts`.
- **Contexto `publico` (Plano 05):** as páginas sem login (página pública `/n/<slug>` e link da consulta antes da assinatura) usam o papel `publico` do `withTenant`, sem ator. **Negado no banco por padrão:** `app_enable_tenant_rls` cria em toda tabela com `tenant_id` (inclusive as antigas e as futuras) a política `RESTRICTIVE` `publico_negado`; só o que o fluxo público usa é liberado, por comando, com `app_allow_publico` — `availability_rules`/`availability_blocks` (`select`), `appointments` (`select`, `insert`), `patients` (`select`, `insert`), `notifications` (`select`, `insert`), `audit_log` (`insert`), `public_booking_requests` (`select`, `insert`, `update`) —, e a lista `PUBLICO_LIBERADO` (`src/db/rls-guard.ts`) tem de bater com o banco (guarda no CI). Sem a política de `UPDATE`, o `publico` não altera paciente e não trava linha de `patients` com `SELECT … FOR SHARE` (a linha some do resultado). Os horários livres saem desse contexto só como intervalos, nunca com dado de outro paciente.
- **Tabelas só da equipe (Plano 05):** `availability_rules`, `availability_blocks`, `whatsapp_conexoes` e `public_booking_requests` têm também a política `staff_only` (a sessão de paciente não vê nem as próprias linhas).
- **Worker:** todo job carrega `tenant_id` no payload e roda dentro de `withTenant`. O worker usa o mesmo role da aplicação (sem `BYPASSRLS`); varreduras entre tenants partem da tabela `tenants`.
- **Métricas do admin:** vêm de uma função `SECURITY DEFINER` que devolve **só contagens** por tenant; o admin nunca executa consultas nas tabelas 🔒. **v1.13 (Plano 11):** também `admin_metricas_ia()` (0099: tarefas e custo do mês por tenant, para a coluna "IA" do admin). **v1.11:** também `admin_metricas_sucesso()` (0087, mesmo molde da `admin_tenant_metrics`: tenant a tenant, recusa rodar dentro de `withTenant`); a guarda `sem-tabelas-tenant.test.ts` confere que todo módulo de `src/modules` importado pelo admin ou é conferido (não acessa tabela com `tenant_id`) ou está na lista dos que só trazem constantes, com o motivo.

### INT-05 — Vídeos (YouTube / Vimeo)

Sem API: a nutricionista cola a URL; o sistema extrai o ID (regex) e renderiza o player com `youtube-nocookie.com/embed/{id}` ou `player.vimeo.com/video/{id}`. A capa é obtida via oEmbed (`youtube.com/oembed`, `vimeo.com/api/oembed.json`) no momento do cadastro e **baixada para `/data`** (sem imagem de terceiros no PWA); se o oEmbed falhar, o cadastro não é bloqueado e o sistema usa uma capa padrão.

**v1.10 (Plano 07, D9, D10):**
- **Links aceitos** (`lerLinkDeVideo`, RN-10): YouTube em `youtube.com`, `www.youtube.com` e `m.youtube.com` (`/watch?v=<id>`, `/shorts/<id>`, `/embed/<id>`, `/live/<id>`) e `youtu.be/<id>`; Vimeo em `vimeo.com`/`www.vimeo.com` (`/<id>`, `/<id>/<hash>` ou `?h=<hash>` do não listado, `/channels/<canal>/<id>`) e `player.vimeo.com/video/<id>`. `https`, `http` ou sem esquema (vale como `https`); sem usuário, senha ou porta; até 500 caracteres. O id (YouTube: 11 caracteres `[A-Za-z0-9_-]`; Vimeo: 6–12 dígitos, mais o hash do não listado) é conferido por regex no código **e** por CHECK no banco. O formulário guarda e mostra o endereço canônico.
- **Player:** `https://www.youtube-nocookie.com/embed/<id>` ou `https://player.vimeo.com/video/<id>?dnt=1` (com `h=<hash>` no não listado); o `src` sai só do id validado, nunca da URL digitada; `iframe` com `title` ("Vídeo: {título}"), `loading="lazy"`, `referrerPolicy="strict-origin-when-cross-origin"` (o YouTube recusa embed sem referrer; vai só a origem) e `allow="encrypted-media; picture-in-picture; fullscreen"`.
- **oEmbed e capa:** ao criar ou trocar o link, **depois** da transação (nunca dentro dela). O servidor só fala com `www.youtube.com/oembed`, `vimeo.com/api/oembed.json`, `i.ytimg.com` e `i.vimeocdn.com` (o link digitado nunca é buscado: o pedido leva o endereço canônico montado do id, sem SSRF), com **prazo total de 5 s** (oEmbed + miniatura), sem seguir redirecionamento, JSON ≤ 64 KB, miniatura só `https` desses dois hosts, ≤ 2 MB, JPEG/PNG/WebP pelo conteúdo. A miniatura vira a capa pelo `processarCapa` (JPEG ≤ 1280 px, qualidade 80, sem EXIF, transparência sobre fundo branco) e entra por `salvarArquivo` (conta na cota). **Qualquer falha** — rede, prazo, HTTP, JSON, host, tamanho, tipo, cota esgotada, erro de disco ou de banco depois de gravado o conteúdo — deixa a **capa padrão** (um bloco com o tipo do conteúdo, sem imagem) e o cadastro segue, sem 500 nem cadastro duplicado. Trocar o link apaga a capa antiga; a capa (ou a remoção) que chega depois do oEmbed só vale se o conteúdo **ainda** aponta para o mesmo vídeo (conferido com a linha travada). Salvar de novo com o mesmo link não refaz o oEmbed. Na receita, a capa é a enviada pela nutricionista.
- **Rede:** o `nutri_app` precisa sair para esses quatro hosts (HTTPS, 443); sem isso, todo vídeo fica com a capa padrão.
- **v1.11 (Plano 08, D12):** o player é **sob demanda** — "Carregar o vídeo" e "O vídeo é exibido pelo YouTube." / "O vídeo é exibido pelo Vimeo."; o `iframe` (mesmos `src`, `title`, `referrerPolicy` e `allow` acima) só entra depois do clique e recebe o foco (RNF-06).

### INT-06 — Cloudflare Turnstile

Widget anti-robô na página pública `/n/<slug>` e na recuperação de senha. O token é validado no servidor (`POST https://challenges.cloudflare.com/turnstile/v0/siteverify`, com `TURNSTILE_SECRET_KEY`) antes de qualquer escrita. Se o Turnstile estiver fora do ar, o formulário público mostra *"Tente novamente em alguns minutos"* e **não** aceita envio sem verificação. Custo: gratuito. **Plano 02:** o E2E usa as chaves de **teste** oficiais da Cloudflare com o `siteverify` real (sem conta), e a validação do ambiente recusa chaves de teste em produção (`NODE_ENV=production` com `APP_URL` fora de `localhost`): *"TURNSTILE_* de teste não pode ser usada em produção"*.

## 8. Regras de negócio

| ID | Regra |
|---|---|
| RN-01 | Cada paciente tem no máximo **1 plano publicado** (garantido por índice único parcial). Publicar arquiva o anterior na mesma transação. Plano publicado é imutável: "Editar" cria uma cópia `rascunho` com `versao + 1`. **Plano 04:** cada paciente tem também no máximo **1 rascunho** (índice único parcial): "Editar" num paciente que já tem rascunho abre o rascunho existente, e só a versão **publicada** se edita (numa versão já arquivada: "Esta versão não está mais publicada. Recarregue a página."). Ao publicar, cada item recebe a cópia dos valores por 100 g e do nome do alimento (`nutrientes`); a tela, o PDF e o portal leem a cópia, então corrigir um "Meu alimento" depois não muda um plano publicado (o "Editar" cria o rascunho com os valores atuais dos alimentos). Modelo não se publica |
| RN-02 | Nutriente do item = `valor_por_100g × quantidade_g / 100`. Totais por refeição e do dia contam **só itens principais** (`substitui_item_id IS NULL`). Indicador × `meta_kcal`: verde se \|desvio\| ≤ 5%; amarelo se 5% < \|desvio\| ≤ 10%; vermelho se \|desvio\| > 10%. Arredondamento na exibição: kcal inteiro, gramas com 1 casa. **Plano 04:** `meta_kcal` vale de 500 a 10000 kcal e a quantidade do item, de 0,1 a 5000 g (a quantidade digitada é arredondada a 2 casas no servidor); alimento sem kcal na TACO ("Sem valor na TACO") conta 0 nos totais, sem `NaN`; a diferença de kcal de uma substituição para o principal só aparece quando os **dois** lados têm kcal na TACO (senão um lado contaria 0 e daria um número clínico enganoso, ex.: "−150 kcal"); o indicador tem texto e desvio, não só cor ("Dentro da meta", "Atenção", "Fora da meta", ex.: "Atenção (+7,5%)"); g/kg usa o peso da última antropometria e, sem ela, mostra "—" |
| RN-03 | Horários livres = regras de atendimento − bloqueios − consultas não canceladas. O paciente agenda com antecedência mínima de `antecedencia_min_h` (padrão 12 h) e máxima de 60 dias. Em caso de agendamento simultâneo, o `EXCLUDE` recusa o segundo e a UI mostra: *"Esse horário acabou de ser ocupado. Escolha outro."* |
| RN-04 | O paciente pode cancelar ou remarcar até `cancelamento_min_h` (padrão 24 h) antes do início. Depois disso, os botões somem e aparece: *"Para alterar, fale com sua nutricionista."* A nutricionista pode alterar a qualquer momento. **v1.8:** até o PWA (P06-09), o paciente age pelo link assinado da consulta enviado por e-mail (`/consulta/<token>`); fora do prazo, só "Avisar que preciso remarcar". Remarcar pelo paciente = cancelar a antiga e criar a nova numa transação; pela nutricionista = "Alterar data e hora" da mesma consulta. **v1.9 (Plano 06, P06-09):** o portal (`/p/agenda/<id>`) tem as mesmas ações do link: "Confirmar presença", "Cancelar consulta" e "Remarcar" dentro do prazo; fora dele, "Para alterar, fale com sua nutricionista." e "Avisar que preciso remarcar"; remarcar leva à página da consulta nova com "Consulta remarcada para {quando}." |
| RN-05 | Lembretes em **24 h** e **2 h** antes do início, por todos os canais disponíveis para o paciente (e-mail sempre; WhatsApp se houver opt-in e cota; push se houver inscrição). O lembrete é **ignorado** (`status = ignorada` + motivo) se: consulta cancelada; paciente arquivado; horário de envio já passou quando a consulta foi criada; horário de envio no intervalo **[21:00, 08:00)** no fuso do tenant (08:00 em ponto é permitido). Remarcar cancela os lembretes pendentes e agenda novos. **v1.8 (D7):** no planejamento, igual. **Na reserva para envio** (worker parado, conta reativada à noite, fila atrasada), o lembrete que venceu e sairia dentro de [21:00, 08:00), na 1ª tentativa, é **adiado para as 08:00** se ainda fizer sentido — o de 24 h, se as 08:00 ficarem antes do lembrete de 2 h (ou até 30 min antes do início quando o de 2 h caiu no silêncio); o de 2 h, até 30 min antes do início —, senão fica `ignorada`/`horario_silencioso`; o de 24 h que sai no dia da consulta diz "hoje". Vale para **e-mail, WhatsApp e push**. Só lembretes: confirmação da marcação, aviso de cancelamento, convite e respostas "1"/"2" saem na hora; novas tentativas não esperam o fim do silêncio. Na **reativação** do tenant, a regra vale ao pé da letra: o lembrete cujo horário já passou fica `prazo_passado` (decisão do dono, 2026-10-02). Lembrete **enviado** não é reaberto: remarcar cria linhas novas para o horário novo. Mudar só a duração, a modalidade ou o link mantém o horário e os lembretes pendentes, **sem aviso próprio** ao paciente (aceito pelo dono, 2026-10-02) |
| RN-06 | Todas as datas são gravadas em UTC (`timestamptz`) e exibidas no `fuso` do tenant. Se o fuso do dispositivo do paciente for diferente, o PWA mostra a sigla junto do horário (ex.: "09:00 (horário de Brasília)") — **v1.9:** no portal, sempre que o fuso do aparelho difere do fuso do tenant (e no servidor, sem saber o do aparelho, com a sigla) |
| RN-07 | Foto do diário: até 10 MB, JPEG/PNG/HEIC; o worker converte para JPEG com no máximo 1600 px no maior lado, qualidade 80, e remove EXIF/GPS. Até **10 registros no diário por paciente por dia**. **v1.9 (Plano 06):** o tipo vem do conteúdo (*magic bytes*); o original é guardado por `salvarArquivo` (`diario_foto_original`, conta na cota) e o worker (fila `diario-foto`) converte e apaga o original; HEIC/HEIF do iPhone é decodificado por **`heic-decode`** (libheif em WASM, só no worker: o `sharp` pré-compilado lê HEIF só com AV1) e entregue ao `sharp` como pixels; imagens acima de **40 MP** são recusadas pelo cabeçalho, **antes** de decodificar ("Não foi possível processar a foto."); a orientação do EXIF é aplicada antes de descartá-lo. A conversão confere a cota **pela diferença** (JPEG novo − original que ele substitui), então trocar o original pelo JPEG nunca é barrado por estar perto do limite. Uma **varredura a cada 15 min** (`expirar-diario-foto`) marca "falhou" o registro preso em "processando" há mais de 30 min sem job vivo e apaga o original (com EXIF/GPS) do disco e da cota; paciente bloqueado ou anonimizado durante a conversão → foto "removida", sem JPEG. O limite de 10 conta registros (com ou sem foto) no **dia do fuso do tenant**, decidido com a linha do paciente travada (corrida de dois envios). O envio aceita uma foto por conta por vez e o corpo tem 60 s para chegar |

| RN-09 | Cota de WhatsApp contada por tenant e mês civil (no fuso do tenant); conta cada mensagem **aceita pela API da Meta** (status `enviada` ou posterior) — **v1.8:** aceita pela Evolution (`enviada_em`): lembretes e avisos de convite; é **limite de uso** (protege o número contra bloqueio e a VPS), não de custo, com padrão 500. ### 9.7 CI/CD (GitHub Actions)

| Gatilho | Etapas |
|---|---|
| Pull request | `pnpm install --frozen-lockfile` → lint → `tsc --noEmit` → Vitest → testes de RLS/isolamento (Testcontainers) → build → Playwright E2E (login, criar+publicar plano, agendar online, lembrete gerado, conteúdo visível só para a audiência certa) |
| Merge na `main` | Build da imagem **no GitHub Actions** (não na VPS, para não consumir CPU e memória do CRM) → push para o GHCR com tag = SHA do commit → chamada ao webhook de deploy do Easypanel → no container do app, `migrate` roda antes do `start` (o worker espera a versão do schema) |

**Deploy e migrations:**
- Ativar no Easypanel o deploy sem downtime (*start-first*), se o recurso estiver disponível na versão instalada. Senão, aceitar ~30 s de indisponibilidade e publicar fora do horário de atendimento.
- Migrations seguem o padrão **expand/contract** (compatíveis com a versão anterior do código), porque as duas versões convivem por alguns segundos. O Drizzle roda cada migration em transação: se falhar, nada é aplicado e o container novo não sobe.
- Rollback = redeploy da tag anterior no Easypanel.
- O primeiro admin é criado pelo comando `pnpm admin:criar <email>` executado no container (sem tela pública); o link de definição de senha (1 h, uso único) sai só no terminal de quem executa. **Plano 01:** até o envio de e-mail existir (P02-01, Plano 02), "Esqueci minha senha" apenas registra um aviso no log, sem entregar e-mail. **Plano 02:** o e-mail existe: "Esqueci minha senha" envia o link pela fila e o convite de nutricionista (72 h) tem token próprio; o convite de paciente (7 dias) fica para o Plano 06.

## Apêndice A — Fórmulas (validar com a nutricionista)

Unidades: peso (P) em kg, altura (A) em cm, idade (I) em anos, soma de dobras (S) em mm.

**IMC** = P / (A/100)². Ex.: 70 kg, 175 cm → **22,86**.

**Harris-Benedict (1919)**
- Homem: 66,47 + 13,75·P + 5,003·A − 6,755·I
- Mulher: 655,1 + 9,563·P + 1,850·A − 4,676·I
- Ex.: mulher, 60 kg, 165 cm, 35 anos → **1370,5 kcal** (exibido como 1371)

**Mifflin-St Jeor (1990)**
- Homem: 10·P + 6,25·A − 5·I + 5
- Mulher: 10·P + 6,25·A − 5·I − 161
- Ex.: homem, 70 kg, 175 cm, 30 anos → **1648,75 kcal**; mulher, 60 kg, 165 cm, 35 anos → **1295,25 kcal**

**FAO/OMS (1985)**

| Idade | Homem | Mulher |
|---|---|---|
| 18 a 29 anos | 15,3·P + 679 | 14,7·P + 496 |
| 30 a 59 anos | 11,6·P + 879 | 8,7·P + 829 |
| 60 anos ou mais | 13,5·P + 487 | 10,5·P + 596 |

Ex.: mulher, 60 kg, 35 anos → **1351,0 kcal**.

**GET** = TMB × fator de atividade (1,00–2,50, informado pela nutricionista).

**Jackson & Pollock — densidade corporal (D)**
- 3 dobras, homem (peitoral, abdominal, coxa): D = 1,10938 − 0,0008267·S + 0,0000016·S² − 0,0002574·I
- 3 dobras, mulher (tríceps, supra-ilíaca, coxa): D = 1,0994921 − 0,0009929·S + 0,0000023·S² − 0,0001392·I
- 7 dobras, homem: D = 1,112 − 0,00043499·S + 0,00000055·S² − 0,00028826·I
- 7 dobras, mulher: D = 1,097 − 0,00046971·S + 0,00000056·S² − 0,00012828·I
- 7 dobras: peitoral, axilar média, tríceps, subescapular, abdominal, supra-ilíaca, coxa

**Siri**: %G = (495 / D) − 450.
- Ex.: homem, 30 anos, S (3 dobras) = 50 mm → D = 1,06432 → **15,08%**
- Ex.: mulher, 35 anos, S (3 dobras) = 60 mm → D = 1,04333 → **24,44%**

Esses exemplos são os casos de teste unitário obrigatórios do cálculo (tolerância ±0,01).

## Apêndice B — Glossário

| Termo | Significado |
|---|---|
| Tenant | A conta de uma nutricionista na plataforma; isola todos os dados dela |
| RLS | Row-Level Security: o Postgres filtra as linhas pelo tenant da sessão |
| PWA | Progressive Web App: site instalável no celular, com push |
| TMB / GET | Taxa metabólica basal / gasto energético total |
| VET | Valor energético total do plano (kcal do dia); base para o % de cada macronutriente |
| TACO | Tabela Brasileira de Composição de Alimentos (NEPA/UNICAMP) |
| Template (WhatsApp) | Mensagem pré-aprovada pela Meta, obrigatória para iniciar conversa (**v1.8:** não usado; a Evolution envia texto simples) |
| Evolution API | Serviço autohospedado que conecta um número de WhatsApp como "aparelho conectado" (Baileys) e expõe envio e webhooks por API REST |
| Link da consulta | Endereço `/consulta/<token>` com assinatura HMAC (128 bits), amarrado ao e-mail do paciente e válido até o início da consulta; enviado só por e-mail |
| Contexto `publico` | Papel do `withTenant` das páginas sem login; negado no banco por padrão, com liberações mínimas por comando |
| Contexto `conta` | Papel do banco (`withConta`) sem tenant, usado só para achar os vínculos de uma conta de paciente; vê só as linhas de `patients` da própria conta (v1.9) |
| Vínculo | A relação (consultório, prontuário) de uma conta de paciente; uma conta pode ter vínculos em mais de um consultório e escolhe um ao entrar (cookie `nd_vinculo`, v1.9) |
| DPA | Contrato de tratamento de dados entre controladora (nutricionista) e operadora (plataforma) |
| RPO / RTO | Perda máxima de dados aceitável / tempo máximo para voltar ao ar |
